Welcome to the PICARD project.

PICARD is a research platform that lets students and faculty run computationally heavy algorithms on a dedicated Hadoop/Spark cluster without having to wire up the infrastructure themselves.

What is PICARD?

PICARD provides a web-based interface to a Spark/Hadoop cluster running on dedicated hardware in a WVU building. Researchers upload their algorithms (Python scripts or Spark JARs) and datasets (as CSVs), configure cluster resources, and submit experiments through a browser. The platform handles authentication, queueing, distributed execution, and result delivery.

The project was originally inspired by Dr. Devine's master's thesis on CoDRIFt, a custom RandomForest algorithm for astronomically large datasets. The original CoDRIFt work required wiring together 20+ PCs by hand to get acceptable performance — PICARD productizes that experience for anyone in the lab.

The three layers

PICARD is built as three loosely coupled layers. Each layer has a single, clear responsibility, and they communicate over well-defined boundaries. Click any card to dive in.

Presentation Layer

React + Vite single-page app. Handles GitHub login, file uploads, experiment configuration, live result polling, visualization, and result downloads. Ships with two themes — the Star Trek LCARS default and an opt-in WVU Light mode. This is what users see and click.

Application Layer

Django + Django REST Framework API. Owns GitHub OAuth, persistence (MySQL), and the experiment queue via Celery + Redis. Celery workers shell out to spark-submit to run jobs. The brain of the system.

Execution Layer

A Spark cluster (master + worker) defined in Docker Compose. Celery tasks invoke spark-submit against the master; results are written to a shared directory and ingested back into Django storage. Where algorithms actually run.

For a side-by-side view of all three layers and how they connect, see the architecture overview.

How a request flows through the system

At a high level, every experiment follows the same path. The frontend collects configuration and hands it to the Django API, the API persists it and queues a Celery task, a worker dequeues it and runs spark-submit against the Spark cluster, the result file is written to the shared directory and ingested back into Django storage, and the frontend polls for status and streams output to the user's browser.

Browser → React (Vite) → Django REST API → MySQL + Celery/Redis → Celery worker → spark-submit → Spark master + worker → Result file
