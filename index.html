Welcome to PICARD.

PICARD is a research platform created to continue Dr. Thomas Devine’s graduate work on scalable machine learning for finding rare transient signals in enormous, highly imbalanced datasets. It helps researchers configure, run, observe, and compare distributed experiments while the platform manages the computing infrastructure.

The problem PICARD exists to address

Signals are rare

Pulsar signals are needles in a cosmic haystack. In one dataset from Devine’s work, only 0.05% of instances represented pulsars.

Datasets are enormous

Radio telescopes produce volumes of data that are impractical for manual review and computationally infeasible for a single machine to process efficiently.

Labels are expensive

Creating trustworthy training data requires expert inspection and can require additional telescope observations, so algorithms must learn effectively from limited labels.

Research is iterative

Researchers need to vary algorithms and parameters, repeat trials, measure both scientific quality and execution performance, and compare the evidence.

From Devine’s research to PICARD

Devine developed a scalable workflow for identifying and classifying transient radio signals. His work produced two distributed Spark algorithms: D-RAPID for candidate identification and CoDRIFt for semi-supervised classification. He evaluated machine-learning choices across tens of thousands of experimental trials.

PICARD carries that work forward as a shared research environment. Its intended form makes distributed experimentation approachable while preserving the rigor of the underlying science: explicit inputs, reproducible configurations, observable execution, meaningful metrics, and comparable results.

Research data→Algorithm + parameters→Distributed execution→Metrics + artifacts→Compare, learn, refine

What kind of project is PICARD?

A scientific experiment platform

PICARD brings research questions, datasets, algorithms, controlled configurations, trials, and evidence into one experiment workflow.

A bridge to distributed computing

The platform handles authentication, queueing, Spark execution, status, and result delivery so researchers can focus on the experiment.

A platform for continued research

Devine’s dissertation identified future work in pipeline scalability, algorithm tuning, additional applications, and streaming. PICARD provides a place for that work to continue.

Why is there a PICARD2?

The first PICARD implementation proved that a browser could submit research jobs to distributed hardware. Its execution path became difficult to operate and extend. Each experiment crossed a .NET API, an in-process queue, orchestration code, and shell scripts that provisioned a fresh Docker Swarm with Hadoop, HDFS, YARN, and Spark. Failures could leave cluster resources or files in an uncertain state, while local development and deployment depended heavily on server-specific knowledge.

PICARD2 is an architectural reset around a smaller set of clearer services: a modern React client, Django/DRF API and data model, Celery with Redis for background work, MySQL persistence, and a persistent Spark standalone cluster managed through Docker Compose. The intent is to make the platform easier to understand, test, maintain, and deploy while preserving its distributed-research purpose.

A shared research missionPICARD2 updates the platform architecture while continuing Devine’s line of accessible, reproducible distributed experimentation. The current work reconnects that cleaner foundation to its scientific purpose.

HorizonProject state

This semesterEstablish one complete research loop: reliably run a thesis-relevant algorithm, view its configuration and scientific results, and conduct a structured parameter sweep that compares multiple trials.
