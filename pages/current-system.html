PICARD2 · active implementation

Where PICARD is today

PICARD2 is the current attempt to turn PICARD into a simpler web application around a persistent Spark cluster. It establishes useful technical pieces, but today it behaves more like a prototype job console than a complete scientific experimentation platform.

Sign in

Users authenticate with GitHub and must belong to the project organization.

Manage inputs

Users can upload, list, share, and delete CSV datasets and Python or JAR algorithm files.

Create a run

The submission page pairs one algorithm with one dataset and accepts an optional free-form argument string.

Watch a run

The runs console lists experiments, polls status, presents an output area, and offers a result download when the API reports one.

Why PICARD was redesigned

No single architecture-decision record explains the rewrite, so the rationale below is inferred from the two codebases and PICARD1’s operational documentation. The strongest reason is not that every earlier framework was obsolete—PICARD1 used React 18 and .NET 8—but that research execution had become tightly coupled to a complex, failure-prone infrastructure lifecycle.

PICARD1 pressurePICARD2 response
Shell scripts built and deployed a fresh Docker Swarm/Hadoop/HDFS/YARN environment for each experiment, then had to tear it down cleanly.Keep one Spark standalone master/worker topology available and submit jobs directly through spark-submit.
The .NET application used an in-process channel while orchestration and job state crossed API code, background services, shell scripts, containers, and files.Give background execution an explicit Celery/Redis boundary and keep web/API persistence in Django and MySQL.
Development depended on a specific remote server, SSH tunneling, old cluster images, and operational knowledge that was difficult to reproduce.Describe the full application as Docker Compose services that can share a consistent local or deployed topology.
The frontend accumulated several overlapping UI libraries and legacy flows around the earlier backend.Start with a smaller React 19 application and a narrower API surface that can be redesigned around the current research journey.

The redesign simplifies the intended architecture; it has not automatically solved reliability. Several research concepts and end-to-end contracts were left incomplete during the reset, which is why the current semester focuses on reconnecting PICARD2 to a proven scientific experiment.

How PICARD2 is organized

React web app→ session + API →Django→MySQL + file storage
Django→Redis queue→Celery worker→ spark-submit →Spark master + worker

A seven-service Docker Compose configuration connects the frontend, API, database, Redis, Celery worker, Spark master, and Spark worker. Unlike the dissertation’s Hadoop/YARN cluster, this implementation uses Spark standalone and keeps the cluster available between experiments.

Architecture principleThe cluster technology may evolve. The durable product concept is an asynchronous experiment that moves from validated configuration through distributed execution to persisted evidence.

What PICARD2 understands today

ConceptCurrent representationImportant limitation
DatasetA named, owned CSV file with public/private visibility.The platform does not describe schema, scientific role, version, or compatibility with an algorithm.
AlgorithmA named, owned Python or JAR file with an optional JAR main class.There is no versioned execution contract or typed parameter definition.
ExperimentAn ID, owner, algorithm, dataset, status, free-form arguments, output/result files, and creation time.The record is not a complete reproducible scientific configuration and has no structured metrics.
ResultAn intended text artifact plus an output file.Logs, result paths, and API behavior disagree, and the portal does not interpret scientific outcomes.

Why the central path is not reliable yet

A code-level review found several disagreements across the API, worker, storage, and frontend:

  • Experiment UUIDs are routed as integers.
  • Saved argument values are not passed to spark-submit.
  • JAR class options are placed in the wrong command position.
  • The worker and API expect different result filenames and locations.
  • The experiment-detail response exposes a file field instead of readable log text.
  • Rerun cleanup, artifact ownership, error detail, and server-side validation are incomplete.

These are implementation problems rather than defining product behavior.

Durable concepts in the current system

Keep the experiment mental model

Users work with datasets, algorithms, configurations, asynchronous runs, and results. Those concepts remain useful when made scientifically precise.

Keep long-running work observable

A researcher needs history, status, logs, errors, and the ability to leave and return without losing the experiment.

Structured configuration

The target experiment model replaces the command-line argument box with typed definitions, defaults, units, constraints, and resolved values.

Elevate the result

Scientific metrics and comparison belong in the primary experience; raw logs and downloadable artifacts are supporting evidence.

Prototype, not finalized productThe current LCARS interface demonstrates available operations. Its navigation, information hierarchy, terminology, and interaction model remain open as PICARD2 reconnects with the research workflow.

What has been validated

Code-level assessment, not runtime certificationThe active experiment, frontend, and Compose paths were reviewed on 2026-08-17. A clean full-stack start, GitHub authentication, and the Spark experiment journey were not run end to end during this assessment.
