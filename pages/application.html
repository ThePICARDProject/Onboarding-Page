Application Layer

The Django backend that owns persistence, authentication, and the experiment queue. Everything that requires durability, authorization, or scheduling lives here.

New generation

This describes the Django backend in picard_new_generation/PICARD2/backend. It replaces the old .NET 8 API. There is no System.Threading.Channels queue, no EF Core, and no Docker Swarm orchestration — the queue is Celery + Redis and the worker calls spark-submit directly.

Celery queue

The queue is the decoupling point between the synchronous HTTP path and asynchronous execution. When a user runs an experiment, the view calls run_db_script.delay(experiment.id) and returns immediately; a Celery worker picks the task up from Redis.

  • The returned AsyncResult.id is stored on the experiment (celery_task_id) so the task can be revoked for cancellation.
  • The broker is Redis (CELERY_BROKER_URL, default redis://redis:6379/0).
  • Tasks are auto-discovered via app.autodiscover_tasks() in backend_config/celery.py.
Key fact Cluster communication is one-way and fire-and-forget: the worker shells out to spark-submit and reads the result file from a shared directory. There is no callback from the cluster.

The worker task (run_db_script)

Defined in experiments/tasks.py. For a single experiment it:

  1. Sets status to Running and initializes the output file.
  2. Builds the spark-submit command, injecting any cluster_config flags (--driver-memory, --executor-memory, --executor-cores, --num-executors) via _build_cluster_args.
  3. Launches it with subprocess.Popen and records the PID on the experiment.
  4. Streams combined stdout/stderr into the experiment's output file line by line (this is what the UI polls).
  5. On exit, ingests the result file from SPARK_SHARED_DIR into Django storage and removes the shared copy.
  6. Sets the final status to Success/Failed — unless a cancel flipped it to Cancelled, which is preserved.

Status lifecycle

Pending → Queued → Running → Success
                              ↘ Failed
                              ↘ Cancelled  (via the cancel endpoint)
StatusSet by
Pendingcreate_experiment (created, not yet queued)
Queuedrun_experiment / run_script on Celery dispatch
Runningrun_db_script when spark-submit launches
Success / Failedrun_db_script based on the subprocess exit code
Cancelledcancel_experiment (preserved by the task)

Cancellation

cancel_experiment only acts on active experiments (Pending/Queued/Running) and is two-pronged:

  1. Revoke the Celery task (revoke(terminate=True, signal='SIGTERM')) so a still-queued task never starts.
  2. Kill the spark-submit PID (os.kill(pid, SIGKILL)) because once the worker is blocked in subprocess.wait(), only killing the OS process actually stops the job.

It then sets status to Cancelled and clears the PID. This mirrors the old gen's ProcessId-based kill — but as a POST, since it mutates state.

Sweep placeholder

PLACEHOLDER · Fall 2026

The sweeps app defines the schema only for the Parameter Sweep Engine: a Sweep model (name, user, script, dataset, parameter_ranges JSON, status, M2M to experiments), a SweepSerializer, and three views (sweep_list, sweep_detail, sweep_cancel) that all return 501 Not Implemented. The full engine — cartesian product expansion of parameter_ranges, batch Celery dispatch, progress aggregation, cancel-all — is a Fall 2026 group deliverable and should live in core/services/sweep_engine.py. See the Sweep model docstring for the full to-do list.
