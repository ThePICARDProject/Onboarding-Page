Execution Layer

The Spark cluster that runs the actual algorithms. In the new gen it is a long-lived Spark master + worker defined in Docker Compose — not a per-experiment Swarm stack.

New generation

The old gen built a fresh Hadoop/YARN/HDFS stack on Docker Swarm for every experiment and tore it down afterward. The new gen runs a standalone Spark cluster (one master, one worker) that stays up; Celery submits jobs to it with spark-submit --master spark://spark-master:7077. There is no YARN, no HDFS, and no per-experiment teardown.

Overview

Everything is orchestrated by docker-compose.yml at the repo root. The relevant cast: a Django backend, a celery_worker, a redis broker, a db (MySQL), a frontend, and the two Spark services. The worker and the Spark containers share a directory so results can be handed back to Django.

The Spark cluster

The master and worker are built from ./spark-cluster and run Spark's standalone daemons directly:

  • spark-master — org.apache.spark.deploy.master.Master. The cluster address is spark://spark-master:7077; the web UI is at :8080.
  • spark-worker — org.apache.spark.deploy.worker.Worker spark://spark-master:7077, configured with SPARK_WORKER_CORES=1 and SPARK_WORKER_MEMORY=1G. Web UI at :8081.

Both mount the Django media directory read-only (so they can read uploaded datasets/scripts) and the shared apps directory read-write. Scaling out is just adding more spark-worker replicas.

Execution flow

The execution layer doesn't orchestrate anything itself — it waits for the Celery worker to submit jobs. From the application layer's run_db_script task:

  1. The worker builds a spark-submit command. spark-submit --master spark://spark-master:7077 [cluster flags] <script> [--class <main>] <dataset> <result-file>. Cluster flags come from the experiment's cluster_config.
  2. It launches the command as a subprocess. subprocess.Popen runs spark-submit; the worker captures combined stdout/stderr and streams it into the experiment's output file (this is the live log the UI polls). The PID is recorded so the job can be killed.
  3. Spark runs the job. The master schedules the work on the worker; the algorithm reads the mounted dataset and writes its result to a unique file in the shared directory (SPARK_SHARED_DIR, i.e. /opt/spark/apps).
  4. The worker ingests the result. When spark-submit exits, the Celery task copies the result file into Django storage, deletes the shared copy, and finalizes the experiment status.

The shared directory

The bridge between Spark and Django is a bind-mounted directory, not HDFS. In docker-compose.yml the host's ./spark-apps is mounted at /opt/spark/apps in the backend, celery_worker, spark-master, and spark-worker containers, and SPARK_SHARED_DIR=/opt/spark/apps is set on the worker.

Per-experiment cluster config

Users can override Spark resources per experiment via the Submit page's Advanced Settings. Those values are stored on SparkExperiment.cluster_config and translated to spark-submit flags by _build_cluster_args in experiments/tasks.py:

cluster_config keyspark-submit flag
driver_memory--driver-memory
executor_memory--executor-memory
cores--executor-cores
nodes--num-executors

An empty cluster_config means "use the cluster defaults" — no flags are added.

Why it looks this way

  • The cluster is long-lived, not per-experiment. Standalone Spark stays up and accepts submissions, so there's no ~3-minute stack build per run like the old Swarm approach. The trade-off is weaker isolation between experiments.
  • Results travel over a shared directory, not HDFS. For a single-host Compose deployment, a bind-mounted folder is the simplest reliable hand-off. The Spark script must write to the result path it's given as its final argument.
  • Concurrency is 1 by default. The Celery worker runs with --concurrency=1, so experiments execute one at a time. Raising concurrency (and worker replicas) is the path to parallel execution.
  • Cancellation kills the OS process. Because the worker blocks on the spark-submit subprocess, the cancel endpoint SIGKILLs the recorded PID — see the application layer.
