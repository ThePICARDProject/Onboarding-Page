System Architecture

A bird's-eye view of how the PICARD new generation is put together. Read this first before diving into any individual layer.

New generation

This describes the Django REST + React rewrite (picard_new_generation). The previous generation was .NET 8 + Docker Swarm + YARN; if you onboarded on that stack, the queue, auth, and execution mechanics below have all changed.

PICARD is a three-layer system. Each layer owns a single concern, and the boundaries between them are deliberately narrow:

  • The presentation layer renders pages and collects user input.
  • The application layer persists state, queues work, and issues commands.
  • The execution layer runs the actual algorithm on Spark.

The architectural choice that shapes everything else is that the application layer doesn't talk to the cluster over an API — a Celery task shells out to spark-submit as a subprocess that writes results to a shared directory. The cluster is treated as a fire-and-forget subprocess. This is simpler than a real RPC layer, and it's the reason cancellation has to kill the OS process directly (see the lifecycle below).

The three layers

Presentation

React + Vite SPA. React Router for navigation, a custom LCARS theme (with an opt-in WVU Light mode), and a small fetch wrapper (src/lib/api.js) that handles CSRF and credentials. Auth and workspace state live in React context providers; sessions are cookie-based.

Application

Django + Django REST Framework. Per-domain apps (experiments, datasets, scripts, authentication, sweeps) expose function-based @api_view endpoints. MySQL for persistence, Celery + Redis to decouple HTTP submission from background execution.

Execution

A Spark master + worker defined in Docker Compose. Celery tasks call spark-submit --master spark://spark-master:7077 as a subprocess, capture stdout into the experiment's output file, and ingest the result file from the shared directory.

The full experiment lifecycle

Every experiment takes the same path. Understanding this end-to-end flow is the single most useful thing you can learn on your first day.

  1. The user configures an experiment in the browser. On the Submit page they pick an algorithm (a .py or .jar), a dataset (a .csv), optional arguments, and — under Advanced Settings — optional Spark cluster resources (executors/nodes, cores, driver memory, executor memory). All of this happens in the React SPA.
  2. The frontend POSTs the config to Django. POST /experiments/create/ creates a SparkExperiment row with status Pending and returns immediately — nothing has run yet. Cluster settings are stored on the experiment as a cluster_config JSON field.
  3. The user queues the experiment. POST /experiments/{id}/run/ sets status to Queued and dispatches a Celery task (run_db_script.delay(id)). The returned Celery task id is saved on the experiment so it can be revoked later.
  4. A Celery worker picks up the task. run_db_script flips the status to Running, builds the spark-submit command (injecting any cluster_config flags), and launches it via subprocess.Popen. The subprocess PID is recorded on the experiment.
  5. Spark runs the algorithm. The worker streams the subprocess's combined stdout/stderr into the experiment's output file line by line, so the frontend can show live logs. The Spark script writes its result to a unique file in the shared directory (SPARK_SHARED_DIR).
  6. The worker ingests the result and finalizes status. When spark-submit exits, the worker imports the result file into Django's storage, deletes the shared copy, and sets the status to Success or Failed (unless the experiment was cancelled mid-run, in which case Cancelled is preserved).
  7. The frontend polls the whole time. The Runs console polls GET /experiments/{id}/ every few seconds while the experiment is active, rendering the live output and updating the status badge. When a result exists, Download, Visualize, and (multi-select) aggregate options appear.
Cancellation

POST /experiments/{id}/cancel/ does two things: it revokes the Celery task and sends SIGKILL to the recorded spark-submit PID. Revoking alone isn't enough — once the worker is blocked in subprocess.wait(), only killing the OS process actually stops the job. (The old gen used a GET kill/:id; the new gen uses POST because it mutates state.)

Layer boundaries at a glance

These are the contracts that connect the layers. If you need to change the contract between two layers, both sides have to move together — otherwise stick to one layer at a time.

Boundary Mechanism Notes
Browser ↔ Presentation HTTP via the Vite dev server / built SPA React Router SPA. API base URL configured via VITE_API_BASE_URL.
Presentation ↔ Application REST over HTTP (Django REST Framework) Session-cookie auth with CSRF token (X-CSRFToken), credentials: 'include'. Live output via polling, not WebSockets.
Application ↔ Persistence Django ORM → MySQL Apps: experiments, datasets, scripts, authentication, sweeps. Standard Django migrations.
Application ↔ Queue Celery → Redis broker HTTP submission returns instantly; run_db_script runs in a worker. Task id stored for revocation.
Application → Execution subprocess.Popen → spark-submit One-way, fire-and-forget. Worker streams stdout and waits for exit code. PID stored so the job can be killed.
Execution → Application Shared directory (SPARK_SHARED_DIR) Spark writes a result file; the worker ingests it into Django storage and removes the shared copy.

A mental model that holds up

If you remember nothing else from this page, remember this:

The model

PICARD is a Django web app that runs spark-submit from a Celery worker. The frontend is a thin React shell over the REST API. The backend is a REST API plus a Celery queue. The queue worker's entire job is to call spark-submit with the right arguments and ingest the result file it leaves behind.

Once you internalize that, most of the system's behavior makes sense:

  • Why does cancel need to kill a PID? Because the worker blocks in subprocess.wait(); revoking the Celery task can't interrupt the already-running child, so the cancel endpoint SIGKILLs the recorded spark-submit PID.
  • Why is live output polled, not pushed? Because the worker just appends subprocess output to a file and the frontend polls the detail endpoint — there's no WebSocket in the new gen.
  • Why are algorithm parameters typed with a driver index? Because they're passed positionally to the Spark job; the driver index preserves their order. See Script.parameters.
  • Why is the sweep engine a placeholder? Because the full Parameter Sweep Engine (cartesian product expansion + batch dispatch) is a Fall 2026 group deliverable. The sweeps app stubs the model, routes, and views (returning 501) so the implementation has a clear home.
