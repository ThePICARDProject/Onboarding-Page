Recommended reading order

  1. Read this portal's Current System, Migration, and Roadmap pages.
  2. Read docs/project-context.md, docs/migration-assessment.md, and docs/codebase-guide.md.
  3. Inspect PICARD2/docker-compose.yml for services, ports, dependencies, and volumes.
  4. Read Django settings/URLs, then dataset, script, and experiment models/views.
  5. Read experiments/tasks.py for the execution lifecycle.
  6. Read frontend lib/api.js, workspace/auth providers, then Submit and Experiments pages.
  7. Consult the matching PICARD1 models/controllers only when analyzing a missing capability.

Runtime baseline: work still required

Setup is not yet reproducibleThe repository has no checked-in safe .env.example, dependencies are not pinned, and a clean full-stack smoke test has not been recorded. Treat the steps below as the baseline task, not a promise that startup will succeed.
  1. Document supported Docker, Compose, Node, and Python versions.
  2. Create a safe PICARD2/backend/.env from an approved example. It must supply Django/MySQL values and local GitHub OAuth credentials; never commit secrets.
  3. From picard_new_generation/PICARD2, validate configuration with docker compose config.
  4. Build and start the stack with docker compose up --build. Expected services are frontend, backend, db, redis, celery worker, Spark master, and Spark worker.
  5. Record migrations, container health, startup failures, and auth prerequisites. Verify the frontend on port 3000, API on 5000, and Spark UIs on 8080/8081 as configured.
  6. Prove the smallest authenticated asset workflow before attempting Spark execution.
  7. Add the commands and fixes to a runbook and automate a smoke test.

A good first contribution

Scope/evidence

Locate sweep artifacts or sample algorithms and connect a capability to concrete legacy evidence and an acceptance criterion.

Reproducibility

Add environment documentation, health checks, test scaffolding, or a clean-start smoke script.

Characterization tests

Cover session behavior, ownership/public visibility, uploads, UUID routes, creation authorization, logs, results, reruns, and deletion.

Vertical-slice repair

Fix one contract only after documenting its intended behavior, then test it across every affected layer.

The first technical priority is UUID route coverage, followed by an explicit execution/artifact protocol and the Python single-run path.

Working principles

  • Preserve the PICARD2 architecture where it is sound; port behavior, not old framework structure.
  • Separate product uncertainty from runtime defects and record both explicitly.
  • Do not call a feature migrated until its end-to-end path is tested.
  • Stabilize one single run before adding orchestration.
  • Use typed configuration and structured results as the boundary for future sweeps.
  • Keep docs, capability status, API contracts, and decisions current as part of implementation.
