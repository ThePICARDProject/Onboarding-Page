PICARD1 → PICARD2

Migration scope

“Complete the migration” means selecting required behavior, implementing it coherently in PICARD2, and proving it end to end. It does not mean reproducing every PICARD1 detail.

Definition of migratedA capability counts only when its complete user path works and has an acceptance test—not when a similarly named model, endpoint, or page exists.

Non-negotiable foundation for sweeps

Typed algorithm parameters

Definitions with order, type, defaults, and constraints—not a longer free-form argument string.

Immutable run configuration

Each single run stores the exact dataset, algorithm version, resolved values, resources, and environment needed for reproduction.

Structured results

Metrics must be queryable and comparable without parsing logs or ad hoc text output.

Reliable operations

Stable states, error metadata, result ownership, cancellation, capacity limits, and recovery must precede multi-trial orchestration.

Decisions the team must make

  • Is the target full PICARD1 parity or a selected core?
  • Are both arbitrary Python scripts and Spark JARs first-class?
  • What files and records define a successful experiment result?
  • Which aggregation, export, and visualization workflows remain valuable?
  • What dataset sizes and deployment constraints must be supported?
  • Can public assets change after experiments reference them?
  • Which per-run Spark resources may users control?
  • Where are the original sweep design and its acceptance criteria?

How to use PICARD1

Consult PICARD1 controllers, models, routes, demos, and sample artifacts when investigating a capability. Extract the intended user behavior and acceptance criteria; do not port ASP.NET, EF Core, Docker Swarm, HDFS, or YARN structure into PICARD2 by default.
