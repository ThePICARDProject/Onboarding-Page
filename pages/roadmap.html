Development roadmap

The team will first turn PICARD2 into a reproducible, explicitly scoped, reliable single-run platform. Hyperparameter sweep implementation follows only after that foundation exists.

Phase 0 · Align scope and preserve evidence

Find the original sweep design, demos, sample jobs, expected results, infrastructure constraints, and stakeholder owners. Mark every legacy capability retain, redesign, or retire.

Exit: agreed parity target and canonical journeys, not “copy PICARD1.”

Phase 1 · Make the repository reproducible

Add safe environment/setup docs, pinned tool versions, health checks, test infrastructure, CI checks, and a one-command startup/smoke path.

Exit: a new developer can clone, configure, start, and verify PICARD2 without oral knowledge.

Phase 2 · Repair one complete experiment

Fix UUID routing, artifact ownership, Python/JAR invocation, argument forwarding, logs, statuses, errors, reruns, and worker recovery. Prove upload → create → queue → execute → log → result download.

Exit: repeatable Python and JAR end-to-end tests pass from a clean database.

Phase 3 · Restore the sweep-ready domain model

Add versioned algorithm definitions, typed ordered parameters, immutable run snapshots, supported resource settings, experiment names/lifecycle data, structured results, and validated API schemas.

Exit: one run is reproducible and its configuration/results are queryable without parsing strings.

Phase 4 · Complete selected parity

Add cancellation; chosen metadata, large-upload, aggregation, export, and visualization workflows; plus versioning, retention, quotas, sharing, and cleanup rules.

Exit: every retained capability has an acceptance test and owner sign-off.

Phase 5 · Adapt and implement hyperparameter sweeps

Revise the prior design against the PICARD2 target model and build bounded, observable multi-trial orchestration.

Exit: the first strategy creates reproducible child runs, respects Spark capacity, and ranks completed trials by a persisted objective metric.

Recommended first backlog

  1. Run a scope workshop using the capability matrix.
  2. Add local setup documentation and test scaffolding.
  3. Fix UUID routing with ownership/authorization coverage.
  4. Write the execution and artifact protocol before changing the worker.
  5. Repair Python single-run execution and download end to end.
  6. Repair the equivalent JAR path.
  7. Add lifecycle timestamps, errors, and cancellation.
  8. Design structured parameter/configuration schemas beside the sweep design.
  9. Implement algorithm definitions and immutable run snapshots.
  10. Reassess aggregation and visualization before porting either.

Post-migration development: sweeps

The intended next feature is hyperparameter sweep orchestration. A sweep should own ordinary child experiments/trials; each child retains one resolved, reproducible configuration.

Design questionDecision required before implementation
Search spacesCategorical, ranges, log ranges, and whether conditional parameters are in the first release.
StrategiesInitial support for grid, random, or another bounded strategy.
CapacityMaximum trials, concurrency, queue policy, and Spark protection.
LifecycleSweep/trial cancellation, retries, partial failures, and resumability.
RankingObjective metric, optimization direction, and structured result source.
ReproducibilitySeed, algorithm version, dataset identity, resolved configuration, and environment.
ExperienceProgress, comparison, best-trial presentation, and export.
Do not extend free-form argsThe current args string cannot safely describe, validate, expand, or compare parameter configurations. Replace it with structured semantics before sweep work.

Artifacts the team must keep current

  • Capability matrix with retain/redesign/retire state, issue/PR, owner, and acceptance-test links.
  • Architecture decision records for orchestration, parameters, results, sharing, and deletion.
  • Versioned API contract or generated OpenAPI documentation.
  • Algorithm execution/input/output protocol for Python and JAR authors.
  • Local/deployed runbook, smoke test, and troubleshooting notes.
  • This portal whenever a capability or phase changes status.
